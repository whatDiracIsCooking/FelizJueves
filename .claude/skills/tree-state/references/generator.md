# The generator

Moved verbatim from `.claude/CLAUDE.md`, "The state of the tree, its table" (indexed by `../SKILL.md`).

**live, for the whole `J` chain, the one-electron matrices and the fused `F`.** `KERNEL_GEN_CMD` in `devtools/config.sh` is `env PYTHONPATH=src python -m felizjueves.emit --L 0 1 2 3 4 5 6 7 8 --pair-l 3 --one-e-l 2` (the PR gate's: `[p\|q]` only through `tiers.DEVICE_L_MAX`, 47 units; `--full` generates `KERNEL_FULL_GEN_CMD`, the same without `--L` / `--pair-l`, 55 units, so L = 9..16 are compiled there and only there — cold, `pq_L16` alone is ~115 s of nvcc), which writes **one ladder per kernel family** (#156) in the backend's spelling (`emit/cuda.py` / `emit/hip.py`). A third backend, `emit/gpu.py`, writes **one text for both compilers** for a consumer that builds either vendor from one tree: each unit includes `include/felizjueves/runtime.h` (FelizJueves's own two headers, `backend.h` and `runtime.h`, no GPU library behind them), which selects the vendor runtime from the compiler's own macros and types the shuffle mask as `FJ_LANE_MASK_T` (`uint32_t` / `uint64_t`); every integer in its text is `int32_t`, never a bare `int` (`CWriter.INT`), and every cast a `static_cast`, one over a sum of launch geometry (`CWriter.cast`; the vendor backends keep `int` and C casts, so no `cuda`/`hip` `source_sha256` moves); a unit with a shuffle also `static_assert`s `FJ_WAVEFRONT` (32 unless built `-DFJ_WAVEFRONT=64`) against the width it was emitted for, and one without has no width in its text. It is the Python API only (not a CLI `--backend`, not in `KERNEL_GEN_CMD`, nothing on a card); `test_emit_gpu.py` holds its goldens (`test/golden/gpu/`) and compiles the same string under nvcc and hipcc, with `conftest.INCLUDE` as the search path `devcache.localize` carries the headers from. A consumer chooses the kernel's name, never the kernel: by default `extern "C" __global__ void s_01(...)`, and with `emit(..., Specialization("s", (0, 1)))` one explicit specialization `s<0, 1>` of a kernel template; `emit_template(kernel, arch, spec, classes)` writes its header `s.h` once, which every unit includes: the primary, defined nowhere (fixed arity, `uint8_t La, Lb, ...` lettered by position, because nvcc 13.0 miscompiles a variadic one's host stub), one explicit specialization declared per class, and `s_kernels`, the consumer's dispatch table indexed by the class's args (`nullptr` where no class was emitted), so a missing class is a link error and a unit whose parameters drifted from the header is a compile error. Only the declarator moves. Each unit compiles as its own TU, launched through the table from another, which nvcc wants as relocatable device code (`-rdc=true`; without it, warning #20280). The device Boys is not carried in a `gpu` unit: `emit_boys()` returns its headers by file name, `eval_boys.h` (`gpu.BOYS_HEADER`) and the `eval_boys_{M}.h` it includes for `M` in 0..`gpu.BOYS_MAX` = 20 (goldens of each), and a unit with a fundamental `#include`s `eval_boys.h` after the runtime and calls `eval_boys<top>`; the consumer writes them all beside the units. `eval_boys<M>` is `BOYS_DEVICE` in this backend's spelling, `static` so every unit's copy stays its own, with the series loop replaced by `eval_boys_series<M>(2T)`: Horner over `gpu.boys_series(M)`, the Kummer coefficients each rounded once from the exact rational, to the least degree whose tail is under 2^-53 of the sum at the switch (40 at M = 0, 61 at M = 20), one `fma` a step and no division or data-dependent exit; `M > 20` is a `static_assert`. `test_eval_boys_device.py` runs it for every M in 0..20 over `BOYS_T` and every switch (worst 1.42e-15 below the switch on the RTX 3080; the RX 9060 XT compile-only, #431). The vendor backends still inline `fj_boys`, loop and all, so no `cuda`/`hip` text or pin moves. Units may still share a TU (`eval_boys.h` is `#pragma once`; records and dynamic shared arrays refused; `emit(..., block_dim=(x, y))` sizes a shared array whose extents are the block's at emit time, a flat `__shared__` declaration with the body unchanged, so `[p\|q]` specializes too, and `emit_template(..., block_dim=)` writes `{template}_block_dim` for the launcher; goldens `pq_22.specialized.cu`, `pq.h`); and `emit(..., any_wavefront=True)` writes **one text for both widths**, opt-in: every shuffle spelled with the header's `FJ_WAVEFRONT` / `FJ_FULL_LANE_MASK`, no `static_assert`, a block-sized shared array `Jsh[10 * FJ_WAVEFRONT]` under `block_dim=(1, gpu.WAVEFRONT)`, the build's `-DFJ_WAVEFRONT` choosing the width at compile time as WarpWraps's `WWR_WARP_SIZE` does (the default text and every pin unchanged; goldens `pq_22.any_wavefront.cu`, `pq.any_wavefront.h`; `test_any_wavefront_device.py` ran it on the RTX 3080 only, wave64 compiled for gfx942, never run) (goldens `s_11.specialized.cu`, `s.h`). With no ladder flag it writes 37 units: the `[p\|q]` ladder (`--L`, default L = 0..16), `build_pq_kernel(L)` — the `[p\|q]` kernel of `[JEngine, v2, Alg. 1]`, default split, **one batch, no atomics**, `pq_L{L}_p{lp}_q{lq}`, byte-identical to before #156 and pinned by `kernels.json`'s `source_sha256` — and the pair ladder (`--pair-l LMAX`, default 3, accepted 0..8), `dq_{la}_{lb}` and `jab_{la}{lb}` for every `la ≤ lb ≤ LMAX` (20 units through (ff)). `--L` alone writes only `[p\|q]`, `--pair-l` alone only the pairs. `--one-e-l [LMAX]` (#242; 3 when bare, accepted 0..8) **adds** the one-electron ladder, `s_{la}{lb}`, `t_{la}{lb}` and `v_{la}{lb}` for every `la ≤ lb ≤ LMAX`, beside whichever J ladders are selected; it is never in the no-flag output, so the 37 units and their pins are unchanged, and `KERNEL_GEN_CMD` asks for `--one-e-l 2` (18 units, through (dd)). The ladder writes `la ≤ lb` only: a real basis keys a class by shell index, so it also reaches `(1,0)`, `(2,0)`, `(2,1)`…, whose units `test/one_electron_driver.py` emits itself (the same text, flags and filter). The emitter casts a scalar parameter the body never reads to `(void)` (`DQ`'s `n_pair`, `JAB`'s `n_rows`), because hipcc's `-Wunused-parameter` otherwise fails #92's filter. The kernel tier generates, compiles its 47 units (29 J-chain, 18 one-electron; 55 with `--full`, the J chain's 37) with nvcc or hipcc, and its device phase (`-m "gpu and <backend>"`) runs, among the rest, `test/test_kernel_device.py` (`J_p` and `fj_boys` on the card against `reference/` in fp64) and `test_j_chain_ondevice.py` (the pair units the tier wrote, and `J` through the whole chain), and `test_one_electron_device.py` / `test_hcore_device.py` (the one-electron units the tier wrote, `S`, `T`, `V` and `h`). **Split classes** are built by `build_pq_kernels(spec)` — one kernel per batch, `J_p` by atomic add — but are **not** written by `KERNEL_GEN_CMD`: the tests emit them (`test_emit_batched.py`, goldens for L = 4, `n_batches = 3`), and the device phase runs the subgrid's split cells and #113's asymmetric cells. **The last full kernel tier on both cards was #157's (PR #210):** 96 passed / 5 skipped on CUDA (RTX 3080), 97 passed / 5 skipped on HIP (RX 9060 XT), the skips the five opt-in recordings (ceilings, `[p\|q]` wall-clock, roofline counters, build wall-clock, sort-key A/B). **The class selector** (#89) is a second, separate CLI path: `python -m felizjueves.emit --class LA LB LC LD` (or `--shell-ls l...`, with `--n-batches N...` and `--admitted-only`) writes, per cell, the whole chain of a real class `(la lb\|lc ld)` a basis reaches, with an `order` file in launch order: `dq_{lc}_{ld}`, the `[p\|q]` batch kernels, `jab_{la}{lb}` (#156); `KERNEL_GEN_CMD` does not call it. `test_ao_j_ondevice.py` compiles the `[p\|q]` slice of those cells in the device phase and builds `J_µν` for H₂ and H₂O/STO-3G on each card against libcint — #89 (PR #118): worst `5.09e-15·scale_J` against a `1e-12` tolerance. **The launch-plan build** (#144) is a third path: `test/plan_driver.py` writes a device `main()` from a `launch.LaunchPlan` that `#include`s each class's emitted units, and `test_j_launched_ondevice.py` compiles and runs it on each card (worst `1.24e-14·scale_J` against libcint over the unscreened cells, identical on both cards). With `chain=` (#157) the same driver adds one `JAB` launch per bra class after every `[p\|q]` launch, and a separate `DQ` program (`plan_driver.dq_program`) supplies its kets: `J` through d with every arithmetic step generated, worst `1.24e-14·scale_J`, the same on both cards. What is **not generated**: the pair list and each record's inputs, the Schwarz bound, the sort and its `Dmax` read-back, the staging, and the launch code (the driver is test-side). The new kernels are **not measured** (no registers, spills, wall-clock or counters), and neither are `S`, `T` or `V`: their register and spill figures are compiler readings in PRs #297 and #298, not store rows. Dispatch is host-side (`performance/dispatch.py`) and reaches only a launch plan. The shipped kernels come from the **literal** plan, by decision: the searched order reaches `build_pq_kernel` only through the opt-in `tuned` lever, which was measured on both cards and refused as the default on wall-clock (#166). One batch is a decision too (`batchreport.ABOUT`); another count goes through the selector, `--class ... --n-batches 1 3 6` (legal: 1 or a positive multiple of 3), and `--n-batches` on the ladder path is rejected with exit 2. The plan-lever device sessions were #162's and #163's A/B device phases (PR #222: 83 passed / 2 skipped on each card; PR #224: 99 passed / 2 skipped on each card); #225 re-runs the full tier. **The last device sessions per card are milestone 12's**, `kernel-tier.sh --backend cuda\|hip -j 6 -- -k 'fock or f_cells'` (exit 0, `device: present`, 55 units compiled with no warning in generated text, then the F device tests): #288 (PR #321) and #290 (PR #324), each **25 passed / 1 skipped on the RTX 3080 and 25 passed / 1 skipped on the RX 9060 XT**, the skip the opt-in F wall-clock, run alone afterwards on each card and passed. They are a `-k` subset, not a full tier. **Milestone 11's tiers were all capped at L ≤ 8 by the user**, and no J text changed, so the L = 16 tier was not re-run; the widest was #244's deferred tier (generator `--L 0..8 --pair-l 3 --one-e-l 3`, 59 units): 95 passed / 3 skipped on CUDA, 96 passed / 3 skipped on HIP, the skips three opt-in recordings. **`K` is not on the ladder:** `KERNEL_GEN_CMD` writes no `K` unit; `kernel_k`'s kernels are emitted by the tests (`test/plan_driver.py`'s `k_driver`, `test_kernel_device.py`'s `K` harness) and by the measured driver (`python -m felizjueves.performance.measured --remeasure --subgrid --target k`). **`F` is not on the ladder either:** `python -m felizjueves.emit --fock-l LMAX` (0..2) or `--fock-class LA LB LC LD` (repeatable; on the 21-class ladder only, so `(10\|00)` exits 2) writes the fused kernel `f_{la}{lb}{lc}{ld}` (#287), a separate path that refuses `--L`, `--pair-l`, `--one-e-l`, `--class`, `--shell-ls` and `--n-batches`; the no-flag output holds no `f_` unit (asserted). All 21 classes are goldens per backend (`test/golden/{cuda,hip}/f_*`), the three over the 512 KiB file cap (`(pd\|pd)`, `(pd\|dd)`, `(dd\|dd)`) pinned by size and sha256 in `test/golden/fock_digests.json`; `(pd\|dd)` and `(dd\|dd)` compile in over 5 s and are `slow`. `test/fock_driver.py` emits the units the device tests run. **The split HGP `J`/`K` is not on the ladder either:** `python -m felizjueves.emit --hgp-j-l LMAX` / `--hgp-k-l LMAX` (any `LMAX >= 0`) or `--hgp-class L0 L1 L2 L3` (repeatable; both targets), with `--ordered` for the ordered mode instead of the canonical one, writes `hj_*` / `hk_*` (#407), a separate path that refuses every other ladder, the selector, the lever flags and `--n-batches`, never in the no-flag output and not in `KERNEL_GEN_CMD`. Its goldens are 126 units per backend (13 canonical and 50 ordered per target, every shell `l ≤ 2`, `test/golden/{cuda,hip}/h{j,k}_*`, no digests file), all compiled under both compilers with no warning in generated text; for that the emitter now casts an unread **array** parameter to `(void)` as well (`emit/_c.py`; no existing unit's text moved). `test/hjk_driver.py` emits the units the device test runs, and that ran on the RTX 3080 only (PR #477; the RX 9060 XT run attached to #431). **The DF metric is not on the ladder either:** `python -m felizjueves.emit --metric-l [LMAX]` (4 bare, any `LMAX >= 0`) **adds** `metric_{lP}{lQ}` for every `lP <= lQ` with `lP + lQ <= LMAX` beside the J ladders (#415), never in the no-flag output (its 37 units and pins unchanged) and not in `KERNEL_GEN_CMD`; it refuses `--class`, `--shell-ls`, `--fock-*` and `--n-batches`. The nine L <= 4 units are goldens per backend (`test/golden/{cuda,hip}/metric_*`); `test/metric_driver.py` emits the units the device test runs, and that ran on the RTX 3080 only (PR #430; #431). **The three-center integral is not on the ladder either:** `python -m felizjueves.emit --eri3-l [LMAX]` (4 bare, any `LMAX >= 0`, a negative one exits 2) **adds** `eri3_{la}{lb}{lP}` for every `la <= lb` with `la + lb + lP <= LMAX` beside the J ladders (#445), never in the no-flag output and not in `KERNEL_GEN_CMD`; it refuses `--class`, `--shell-ls`, `--fock-l`, `--fock-class` and `--n-batches`. Its names come from `kernel_eri3.eri3_name` (`_`-separated once any `l > 9`, so `(0,11,0)` and `(0,1,10)` no longer share `eri3_0110`). The 22 L <= 4 units are goldens per backend (`test/golden/{cuda,hip}/eri3_*`; the largest, `eri3_220.hip`, is 58,818 B, so no digests file); `test/eri3_driver.py` emits the units the device test runs, and that ran on the RTX 3080 only (PR #457; the RX 9060 XT run attached to #431). **The dipole is not on the ladder either:** `python -m felizjueves.emit --mu-l [LMAX]` (2 bare, **0..3 only** since #627, exit 2 above: the dipole is validated through (ff) only, on the host, interpreted and compiled, and on the cards through (dd)) **adds** `mu_{la}{lb}` for every `la <= lb <= LMAX` beside the J ladders (#522), never in the no-flag output and not in `KERNEL_GEN_CMD`; it refuses `--class`, `--shell-ls`, `--fock-l`, `--fock-class`, `--n-batches` and the HGP path. The six units are goldens per backend (`test/golden/{cuda,hip}/mu_*`, no digests file); `test/mu_driver.py` emits the units the device test runs (every ordered class it needs), and that ran on both cards (PR #546). Set `KERNEL_GEN_CMD=` and the tier reports generate/compile DORMANT — do not read that as green.
